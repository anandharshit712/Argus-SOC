Argus SOC with Talos

How the whole system works, end to end. Talos reads security logs and detects attacks one incident at a time. Argus SOC loads those incidents into a FalkorDB graph, where three agents connect them, follow them to what matters, decide what to do, and remember what the analyst said for next time.

Talos: detection, already built Argus SOC: graph and agents, built during the event Memory and feedback

Talos sections describe the code in the Talos repo as it stands. Argus SOC sections describe the plan for Oct 15–18; anything marked proposed is a starting rule we will tune while building. Actions such as "isolate host" are simulated: recorded in the graph and shown in the UI, never sent to real infrastructure.

Part 1 · For teammates new to Talos

    
How Talos works

    
Talos is Harshit's open-source attack-detection engine (github.com/anandharshit712/Talos, Apache licence). It reads web and network security logs one event at a time and answers three questions about each attack: is it an attack, which technique is it (mapped to MITRE ATT&CK and OWASP), and what exactly was affected, including whether it succeeded. In Argus SOC we run Talos unchanged and read its incidents over HTTP.

    

      

        
Rule 1 · Deterministic first, model second

        
Regex and statistics make the detection decision. A language model is called only for genuinely borderline cases and to write the narrative. With no model reachable, every detector still works and marks its verdict used_llm=false.

      

      

        
Rule 2 · Every verdict carries evidence

        
Each verdict has a confidence between 0 and 1 and non-empty evidence: the matched pattern, the computed statistic or the baseline deviation, plus the event IDs behind it. A score without evidence is never shipped.

The detectors

    

      

        
DetectorCategoryMITREFires when

        
          
SQL injectioninjectionT1190SQL pattern rules hit. A clear hit (for example UNION SELECT) is a verdict with no model call. A borderline hit goes to a code-aware model whose only job is to clear it; with no model reachable it becomes a low-confidence lead.

          
XSSinjectionT1059.007Same approach with XSS pattern rules.

          
Web brute forceauth_failureT111010 or more failed logins within 120 s against one account or from one IP.

          
Credential stuffingauth_failureT1110.00415 or more distinct accounts within 300 s, with at most 3 failures each: breadth rather than depth.

          
SSH brute forcenetwork_brute_forceT11108 or more failures within 120 s.

          
RDP brute forcenetwork_brute_forceT11108 or more failures within 120 s.

          
IDORbroken_access_controlT1083, T1530Each account has a learned access baseline. A score weighs four features: sequential object ids 0.40, ids outside the usual range 0.30, access rate 0.20, new endpoint 0.10. Silent below 0.35. Above it, a reasoning model weighs in with a 0.40 weight. Until a baseline has 50 observations, it only emits a 0.20-confidence lead that never fires.

        
      

    

    
Rate-based confidence (all four login detectors): 0.70 at the threshold, plus 0.02 for each extra failure, capped at 0.95. A burst followed by a successful login never scores below 0.90.


    

      

        
How an incident is scored

        
    
          
  • Severity floor by category: injection high, access control high, auth failure medium, network brute force medium.
    • 
          
  • One level up if the attack succeeded. One level down if confidence is below 0.5.
    • 
          
  • Confidence: the highest verdict, plus 0.05 for each extra independent detector that agrees.
    • 
          
  • Recommended actions: templates per category (block IP, force password reset, patch endpoint, revoke session), plus "rotate credentials" and "hunt for follow-on activity" when it succeeded.
    • 
        

      

      

        
Where models are used

        
    
          
  • Placing events the static classifier rules cannot place.
    • 
          
  • Judging borderline injection payloads (it can only clear them).
    • 
          
  • Weighing IDOR scores above the floor.
    • 
          
  • Writing the narrative for each verdict.
    • 
        

        
Each detector and classifier has its own routed model on Groq, NVIDIA NIM or Mistral. With no keys, Talos produces the same incidents with templated narratives.

What Talos does not do, and why Argus SOC exists

      
    
        
  • It never links one incident to another. An SSH brute force and a credential-stuffing burst from the same IP are two unrelated reports.
    • 
        
  • It does not know the environment: which hosts connect to which, who logs in where, which servers hold the crown jewels.
    • 
        
  • It does not remember analyst decisions across sessions.
    • 
        
  • It recommends actions but does not decide or act.
    • 
      

    

  


  
  

    
Part 2 · What we build Oct 15–18

    
How Argus SOC works

    
Argus SOC turns Talos's separate incidents into one connected picture per client company, then runs three agents over it. Every agent decision comes from a Cypher query or graph algorithm, and every decision and analyst verdict is written back into the graph as memory. FalkorDB is the only place Argus SOC keeps state.

What runs in parallel, what runs in order

    

      

        
PartHow it runs

        
          
Talos, per eventIn order: parse → window → route → classify → sub-agent → aggregate → suppress → store

          
Detectors inside one Talos sub-agentParallel (asyncio.gather): SQLi ∥ XSS, brute force ∥ credential stuffing, SSH ∥ RDP

Graph writesOne short MERGE query per write, so parallel agents don't clash

          
AnalystAsynchronous: the case waits in the UI queue until someone acts

        
      

    

  


  
  

    
Part 4

    
The loops

    

      
↻
Talos repeat suppression
Every event past a detector's threshold fires again. Talos remembers each attack's signature (category, technique, accounts, hosts, endpoints) and reports again only when the attack succeeds or its attempt count doubles. Old signatures expire by event time.

      
↻
Talos IDOR baseline
Every object access is scored against the account's baseline and then added to it. The baseline grows with use, capped at 500 object ids and 50 endpoints per account.

      
↻
Ingestor polling
The ingestor asks Talos for new reports every few seconds. Because every write is a MERGE on incident_id, overlapping polls never create duplicates.

      
↻
Case handoff and resume
Each agent finishes by recording a handoff and setting the case status. The next agent picks up cases in that status. If an agent crashes, it restarts, reads the case from the graph and carries on.

      
↻
Learning across sessions
Analyst feedback → Playbook version → Triage checks playbooks first next session. This is the loop that proves Track 02: memory that persists, updates and is shared by every agent.

      
→
After the hackathon: back into Talos
Push learnings back into Talos, for example suppressing a detector for a source known to be benign. Not in hackathon scope: for now Talos stays unchanged and all learning lives in the graph.

    

  


  
  

    
Part 5

    
Glossary

    

      
SOC
Security operations centre: the team that watches alerts and responds to attacks.

      
IOC
Indicator of compromise: a concrete trace of an attacker, here a source IP.

      
MITRE ATT&CK
A public catalogue of attacker techniques with IDs such as T1110 (brute force).

      
Credential stuffing
Trying leaked username and password pairs across many accounts, a few attempts each.

      
IDOR
Insecure direct object reference: reading objects you shouldn't by changing an id in the URL.

      
Crown jewel
A host holding the most valuable data, such as the production database.

      
Blast radius
Everything an attacker's IP or stolen account has touched or can reach.

      
Connected components (WCC)
A graph algorithm that groups nodes linked by any path; used to group related alerts into one case.

      
Centrality / PageRank
Algorithms that score how important a node is to the network's connections; used to pick which host to isolate first.

      
Tenant
One client company. Each gets its own FalkorDB graph, so memory never crosses between companies.

      
Cypher
The graph query language FalkorDB uses.

      
MERGE
A Cypher write that creates a node or link only if it doesn't already exist.
